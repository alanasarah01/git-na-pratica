Sequência progressiva pra praticar em projetos pessoais, do básico ao realista
Bloco 1 — 🌿 Simulando conflito real: tabela 2 vs tabela 3 Fluxo guiado

Fluxo pra vivenciar rebase/merge de verdade em projeto pessoal.

MAIN

1. Ponto de partida

A main está com o projeto inicial das camadas.

BRANCH TABELA-2

2. Cria branch a partir da main

Você cria feature/tabela-2 baseada na main atual e começa a trabalhar nela.

BRANCH TABELA-3

3. Cria a segunda branch (ainda sem mergear a primeira)

Antes de abrir o PR da tabela-2, você já cria feature/tabela-3 — também a partir da main, que nesse momento ainda não tem as mudanças da tabela-2.

MERGE

4. Mergeia a tabela-2 primeiro

Você finaliza feature/tabela-2, abre o PR e faz o merge na main. Agora a main está "à frente" da branch tabela-3.

DIVERGÊNCIA

5. Tenta abrir o PR da tabela-3

A branch feature/tabela-3 ainda está baseada na main "velha" — ela não tem as mudanças da tabela-2. Se mexeu no mesmo arquivo, isso gera conflito.

RESOLVE

6. Traz o estado novo da main pra sua branch

Você roda git pull origin main (merge) ou git rebase main dentro da feature/tabela-3, resolve os conflitos manualmente, e só depois abre o PR.

Por que fazer isso de propósito: esse é exatamente o tipo de situação que acontece em time real — duas pessoas mexendo em branches diferentes, uma mergeia primeiro, a outra precisa atualizar a branch antes de finalizar. Treinar isso sozinho, num projeto de baixo risco, é o jeito mais seguro de aprender antes de passar por isso em produção.

🗓️ Plano de exercícios — 4 blocos práticos

Do básico ao realista, cada bloco com vídeos sugeridos
Bloco 2 — Fundamentos do fluxo Aquecimento

1. Amend — corrigir o último commit

Esqueça um arquivo no commit ou erre a mensagem de propósito, depois use git commit --amend pra corrigir antes de subir.

Objetivo: perder o medo de mexer no commit mais recente

2. Stash — pausar um trabalho no meio

No meio de uma alteração, simule uma urgência: rode git stash, troque de branch, resolva algo, volte e dê git stash pop.

Objetivo: trocar de contexto sem perder nem misturar trabalho

Bloco 3 — Corrigindo erros Recuperação

3. Commit direto na main sem querer

Commite direto na main por engano. Depois resgate: crie uma branch nova a partir desse ponto e volte a main pro estado anterior.

Objetivo: saber resgatar trabalho sem perder nada

4. Revert vs reset

Suba um commit "errado" de propósito. Pratique desfazer com git revert (seguro, histórico preservado) e, em outro cenário local, com git reset --soft.

Objetivo: entender quando cada um é seguro de usar

5. Commit "sujo" demais

Misture três mudanças diferentes num commit só. Depois separe com git reset --soft HEAD~1 e recomite em partes organizadas.

Objetivo: aprender a quebrar commits em unidades lógicas

Bloco 4 — Conflitos reais O ponto principal

6. Branch desatualizada

Comece a trabalhar numa branch sem dar pull antes. No meio do caminho, perceba que a main avançou e precise ratrapar com git rebase main.

Objetivo: sentir a dor de trabalhar "atrasado"

7. Conflito real (tabela-2 vs tabela-3)

O cenário que já montamos: duas branches a partir do mesmo ponto, uma mergeia primeiro, a outra precisa atualizar e resolver conflito antes do PR.

Objetivo: resolver conflito de verdade, não só ler sobre ele

8. Conflito em arquivo de config (.yml)

Repita o conflito, mas agora num sources.yml ou schema do dbt. Conflito estrutural é mais sutil que em código.

Objetivo: praticar conflito no tipo de arquivo comum em dados

9. A regra de ouro do rebase

Entenda por que git rebase nunca deve ser feito em branch pública (compartilhada por outras pessoas, como main ou development). Rebase reescreve o histórico e muda os hashes dos commits — se alguém já baseou trabalho nesses commits, um push --force depois do rebase pode sobrescrever ou até apagar o trabalho de colegas. Rebase só é seguro na sua branch pessoal, que mais ninguém está usando.

Objetivo: saber quando rebase é seguro e quando é perigoso

10. Backup de branch antes de operação arriscada

Antes de rodar um rebase ou reset que você não tem 100% de certeza, crie uma cópia de segurança: git checkout -b nome-backup a partir da sua branch atual, volte pra branch original e só então aplique a operação. Se algo sair errado, o backup está intacto.

Objetivo: ter uma rede de segurança pra experimentar sem medo

Bloco 5 — Organização avançada Polimento

11. Squash antes do PR

Faça 6-8 commits pequenos e "sujos" numa branch (tipo "ajuste", "ajuste2"). Antes do PR, use git rebase -i pra juntar tudo num commit limpo.

Objetivo: entregar histórico organizado pro revisor

12. Cherry-pick

Tenha uma correção específica numa branch e traga só ela pra outra branch, sem trazer o resto do trabalho, usando git cherry-pick.

Objetivo: mover mudanças pontuais entre branches

13. Limpeza pós-merge

Depois que um PR é aceito, delete a branch local e remota: git branch -d nome e git push origin --delete nome.

Objetivo: manter o repositório organizado, hábito de time
